# v80：将 DPU 等待移到独立工作线程

v72改善触控轮询后，显示路径仍包含外层DPU等待。v73增加阶段计时，后续版本加入SMP和CPU EPSS请求支持；v80在精确v79候选上替换呈现入口与统计分配、清理钩子，使完整帧生成和显示提交由两个线程协作。

## 状态与所有权

呈现线程在同一把锁下等待空闲目标和空待提交槽，调用原计时/合成路径生成完整帧，确认目标为READY且ticket匹配，再发布目标编号并唤醒工作线程。帧尚未完成时不得发布。原呈现器随后按原顺序释放源引用、清理保留内存并退休生产者fence。

工作线程只操作自有目标与pipeline状态，不保留或解引用源表面、swap或源framebuffer。它轮询真实继承的DPU完成条件，完成后提交待显示目标；忙时释放锁再执行50us延时，空闲时睡眠。缓冲不足时呈现线程施加背压。初始化失败沿用原同步呈现；运行失败停止继续使用状态并保留分配。

停止标志使用acquire读取。工作线程退出活动循环后停驻，清理调用原SMP OFF、GPU/DPU恢复和CPU恢复路径；分配保留至RAM返回。这不是可卸载的通用驱动生命周期。

## 验证

公开副本重新运行主机ASan/UBSan并发集成检查：12场景、512帧流。原冻结审查还记录TSan、11个实际链接ARM64场景、18个准入场景，以及3个编译后变异被拒绝；这些历史报告不等于本次重新执行全部原生或硬件测试。

实机45秒观察中：异步入队780、提交780、计数完成779；GPU完整复制776/776，合格帧CPU复制0，普通路径4；源781/781退休，GPU4901/4901。Android恢复且原boot/dtbo哈希一致。新严格准入通过，整体仍INCOMPLETE，独立旧校验器失败于verify-lmi-gpu-gx.py:11的HFI DCVS请求断言。原校验器与日志未改写。

`pending`打印为UINT64_MAX代表内部int -1，表示无待提交槽，不是巨量积压。该槽为空也不代表最后扫描已完成。不能把提交计数等同完成计数。

没有测得屏幕动画FPS、物理渲染/扫描重叠、触控到光子延迟或受控跨版提升倍数。FRAME/SOURCE/COPY存在重叠，GAP/CADENCE混有空闲与调度，不以倒数推导动画FPS。EPSS请求索引读回不是实测CPU频率。Wi-Fi未集成。
